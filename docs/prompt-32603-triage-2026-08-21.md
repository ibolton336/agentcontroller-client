# `prompt failed: prompt error -32603: Internal error` — triage (2026-08-21)

Run: pod `ui-d7kdf`, app Hub (id=2), repo jortel/tackle2-hub, harness image built from
konveyor/agentic-controller PR #157 lineage (no `ask_user tool mounted` line → not the
#161 harness), goose pinned at **v1.45.0** (same pin on main, #157 and #161 since #53).

## Resolution (added 12:50, after the Gateway was shared)

The run's Gateway is `provider: gcp-vertex-ai`, `endpoint: https://global-aiplatform.googleapis.com`,
`model: claude-sonnet-4-5@20250929`, `credentialRef: {secretName: vertex-credentials}` — byte-for-byte
the PR #140 sample (`config/samples/gateway_vertex_ai.yaml`), on a teammate's cluster set up from
the #140 getting-started guide (Option A) and launched from the console.

* The provider *name* is fine: the harness normalizes `gcp-vertex-ai` → `gcp_vertex_ai`, which is
  goose's Vertex provider. "Won't work with gcp-vertex-ai" is the wrong conclusion.
* What breaks: #140's Secret recipe carries only `GOOGLE_APPLICATION_CREDENTIALS_JSON`. goose
  1.45's `GcpVertexAIProvider::from_env` starts with `config.get_param("GCP_PROJECT_ID")?` — no
  default, errors instantly — and the harness forwards nothing else for Vertex (`providerEnv`
  only writes the ADC file; it ignores the Gateway `endpoint`). That error is the one goose
  swallows at `session/new` (`create_agent_locked` → `warn!`), so the first prompt fails with
  `Error getting agent reply: Provider not set` → the bare `-32603` after 41 ms. Timing fits:
  no network involved.
* Second latent problem once the project id is present: `GCP_LOCATION` defaults to
  `us-central1`; the Gateway's `global` endpoint never reaches goose. Requests would go to
  `us-central1-aiplatform.googleapis.com` for a model published on `global`/`us-east5` — a
  provider error, which goose turns into an assistant message → the run "succeeds" with no
  commits. `GCP_LOCATION=global` in the same Secret fixes it (goose maps `global` to
  `https://aiplatform.googleapis.com`).
* gcloud's `application_default_credentials.json` (`authorized_user`) is accepted by goose's
  `GcpAuth` (refresh-token exchange at request time), so the credential file itself is fine.
* The Gateway's `Ready / ConnectionVerified` only proves the endpoint answers HTTP; it says
  nothing about Secret keys, project or location.

Fix for the cluster owner (same as my unaddressed #140 comment,
https://github.com/konveyor/agentic-controller/pull/140#discussion_r3797472651):

```bash
kubectl -n <ns> create secret generic vertex-credentials \
  --from-file=GOOGLE_APPLICATION_CREDENTIALS_JSON="$HOME/.config/gcloud/application_default_credentials.json" \
  --from-literal=GCP_PROJECT_ID="$(gcloud config get-value project)" \
  --from-literal=GCP_LOCATION=global \
  --dry-run=client -o yaml | kubectl apply -f -
```

then re-run (no image change needed). Still worth doing regardless: the harness printing
`error.data`, and #140 adding the two `--from-literal` lines.

## What the log proves

| t (s) | line | meaning |
|---|---|---|
| 09.298 | ACP initialized | handshake OK |
| 09.429 | ACP session created | `session/new` OK (131 ms) |
| 09.429 | max turns: 200 | `session/prompt` sent |
| 09.470 | prompt failed: -32603 Internal error | goose rejected the prompt **41 ms** later |

* `-32603` is the JSON-RPC response to the harness's own `session/prompt` on the
  goose loopback (:4001), not something from the tee/viewers.
* goose attaches the real reason as `error.data` on every internal-error site on
  that path (`Error getting agent reply: …`, `Error in agent response stream: …`).
  The harness's `SendPrompt` formats only `code: message`
  (`harness/internal/acp/session.go`, both `prompt error %d: %s` sites) and
  `RPCError.Error()` returns only `Message` (`jsonrpc.go`) — the `Data` field is
  parsed and thrown away. So the cause is not recoverable from this log.
* `goose serve` logs to a file only (`setup_logging` → `console: false`), under
  `$HOME/.local/state/goose/logs/cli/<date>/` with `HOME=/home/harness` in the
  agent image. That file died with the container.

## What goose 1.45.0 does on `session/prompt` (why 41 ms matters)

1. Provider/model failures during the turn (Bedrock 4xx, auth, region, network)
   are **not** RPC errors: the reply loop converts them into an assistant message
   ("Ran into this error: …") and ends the turn normally
   (`crates/goose/src/agents/agent.rs`, reply loop `Err(ref provider_err)` arms).
   A run hitting those would *succeed* with no commits — not fail like this.
2. Therefore `-32603` on prompt = goose tripped **before the model call**. The
   first hard `?` in `reply_impl` is
   `check_if_compaction_needed(self.provider().await?, …)` → `"Provider not set"`
   → `Error::internal_error().data("Error getting agent reply: Provider not set")`.
3. How an agent ends up with no provider although `session/new` succeeded:
   `execution/manager.rs::create_agent_locked` calls
   `restore_provider_from_session`; on failure it only `tracing::warn!`s and keeps
   the agent. `goose serve` never calls `set_default_provider`, so nothing backfills
   it. `session/new` returns OK; the first prompt fails instantly. This matches the
   timing exactly (no network needed).
4. (Written before the Gateway was known; kept for the Bedrock case.) What makes `restore_provider_from_session` fail for `aws_bedrock`
   (`providers/bedrock.rs::from_env`), fastest first:
   * provider name not in goose's registry (Gateway `spec.provider` after the
     harness's lower-case/`-`→`_` normalization must be exactly `aws_bedrock`);
   * `AWS_BEARER_TOKEN_BEDROCK` set but no region resolvable;
   * credentials unresolvable (`provide_credentials()` fails; only fast if the
     default chain's IMDS probe is rejected immediately — `session/new` took 131 ms,
     so a hanging IMDS probe is ruled out);
   * (unlikely) session DB persist failure in `update_provider`.
   Keyless Bedrock creds reach the pod via `envFrom` on the Gateway's Secret — that
   wiring is unchanged between main and #157 (`agentrun_controller.go`,
   `EnvFrom: append(envFrom, run.Spec.EnvFrom...)`).

## Relation to PR #157

* Harness delta vs main: `api/skill` module in the build, rules injected into the
  prompt. With no skills mounted `ReadManifest` returns an empty manifest and the
  `## Rules` section is omitted — the prompt bytes are identical to main's. Nothing
  in #157 touches goose launch, provider env mapping, or the ACP prompt path.
* Controller delta: skill-loader init container, skills mount, `KONVEYOR_SKILL_SOURCES`.
  Env/envFrom/credential wiring unchanged.
* CI at head efc511f is green, but the e2e Gateway is `provider: openai` against an
  emulator with an API-key `credentialRef` — it never exercises keyless Bedrock.
* No issue/PR on the repo mentions `-32603` or `prompt failed` as a live failure.

Conclusion: this failure is outside #157's scope and #157 is not a plausible cause;
it also neither validates nor indicts #157 (the run never reached the model).
