# Remediation-branch review (4-lens, empirically verified)

## Summary
Synthesis of 4 lens reviews (build, cdi-tx, messaging, completeness) of the coolstore remediate branch. Consensus, empirically verified by the messaging lens actually building/running the branch: exactly two compile blockers (quarkus-rest-jackson absent from the 3.8.4 BOM; Flyway 4 API in DataBaseMigrationStartup) which validate WILL catch and can fix with a one-line artifact rename + one class deletion. After that, mvn compile goes green on an app that cannot start: SRMSG00073 dual-direction 'orders' channel (prod), unknown smallrye-in-memory connector (dev), and a stack of silent semantic breaks (dead inventory-notifications channel, global shared cart, @SessionScoped endpoint without undertow, lost /services base path, Hibernate 6 sequence mismatch, system-scoped audit jar excluded from packaging, orphaned webapp UI) that a compile-only validate stage will wave through to the demo PR. Key demo risk: validate as specified (mvn compile + minimal fixes) reports success on a non-startable app — the validate gate should be package + app start, on JDK 17/21.

## Ranked findings

1. [will-break-compile | CAUGHT by validate] pom.xml — io.quarkus:quarkus-rest-jackson does not exist in the Quarkus 3.8.4 BOM (artifact name is 3.9+; 3.8 name is quarkus-resteasy-reactive-jackson). Verified: every mvn invocation dies at POM model validation with "'dependencies.dependency.version' for io.quarkus:quarkus-rest-jackson:jar is missing @ line 37" — masks all other errors until fixed. Fix: rename artifactId (or bump platform to 3.15 LTS and also rename quarkus-smallrye-reactive-messaging-amqp→quarkus-messaging-amqp).

2. [will-break-compile | CAUGHT by validate] src/main/java/com/redhat/coolstore/utils/DataBaseMigrationStartup.java:35-36 — `new Flyway()` and `flyway.setDataSource(...)` are Flyway 4 APIs removed in flyway-core 9.22.3 (pinned by the 3.8.4 BOM via quarkus-flyway); verified javac errors. Correct minimal fix is DELETE the class: quarkus.flyway.migrate-at-start=true + classpath:db/migration already run both migrations (verified in startup log), and the class's unconditional baseline() would corrupt/throw on every boot even if ported.

3. [wrong-semantics | SURVIVES mvn compile; caught only if validate STARTS the app] src/main/resources/application.properties — channel 'orders' is configured both mp.messaging.incoming.* and mp.messaging.outgoing.* while the emitter (@Channel("orders") in ShoppingCartOrderProcessor) and consumer (@Incoming("orders") in OrderServiceMDB) share the name. Verified on the packaged app: DeploymentException SRMSG00073 'channel names cannot be used for both incoming and outgoing: [orders]' — prod startup hard-fails. Fix: distinct channel names joined via .address=orders, or drop connectors for in-process wiring.

4. [wrong-semantics | SURVIVES mvn compile; caught only if validate runs quarkus:dev] src/main/resources/application.properties — %dev profile sets connector=smallrye-in-memory but io.smallrye.reactive:smallrye-reactive-messaging-in-memory is not in pom.xml. Verified in quarkus:dev: 'Found 3 deployment problems: unknown connector (smallrye-in-memory)'. Even if added, the in-memory connector does not loop outgoing→incoming, so dev-mode orders would be silently dropped. Fix: delete the three %dev messaging lines (in-process auto-wiring) — note Dev Services will then want Docker unless quarkus.amqp.devservices.enabled=false.

5. [wrong-semantics | SILENTLY SURVIVES everything — no error ever] src/main/java/com/redhat/coolstore/service/InventoryNotificationMDB.java + application.properties — topic fan-out severed: on main BOTH MDBs subscribed to JMS topic topic/orders; now the sole emitter feeds only 'orders' and @Incoming("inventory-notifications") is bound to an AMQP address nothing publishes to. Low-stock notification path is permanently dead code. Demo fix: @Broadcast on the emitter with both consumers on 'orders' (in-process), or a multicast broker address — plain address sharing round-robins (anycast) and still regresses topic semantics.

6. [wrong-semantics | SURVIVES compile AND package (empirically verified); fails at first /cart request] src/main/java/com/redhat/coolstore/rest/CartEndpoint.java:24 — still @SessionScoped with no quarkus-undertow in the pom (analyzer insight 11 explicitly warned); RESTEasy Reactive registers no session context → ContextNotActiveException the moment the demo touches the cart. Fix: @RequestScoped.

7. [wrong-semantics | SILENTLY SURVIVES — logic bug, no error] src/main/java/com/redhat/coolstore/service/ShoppingCartService.java — @Stateful→@ApplicationScoped kept `private ShoppingCart cart = new ShoppingCart()` and getShoppingCart(cartId) ignores cartId: one unsynchronized global cart shared by all users; checkout resets everyone. The plan's own 'session redesign' warning was recorded then ignored. Fix: ConcurrentHashMap<String, ShoppingCart> keyed by the cartId already threaded through every REST route (masked in a single-user demo).

8. [wrong-semantics | SILENTLY SURVIVES — 404s only] RestApplication.java deleted (@ApplicationPath("/services")) with no quarkus.resteasy-reactive.path=/services replacement — endpoints moved from /services/* to /*; the shipped frontend hardcodes /services/cart and /services/products (src/main/webapp/app/services/cart.js:9, catalog.js:9) and any demo curl script using old paths 404s.

9. [wrong-semantics | SILENTLY SURVIVES until first order insert] src/main/java/com/redhat/coolstore/model/Order.java:24, OrderItem.java:18 — hibernate-00005 insight unaddressed: bare @GeneratedValue under Hibernate 6.4 defaults to per-entity ORDERS_SEQ/ORDER_ITEMS_SEQ but Flyway's V1_1__CreateSchema.sql creates only hibernate_sequence → first checkout that persists an order throws sequence-not-found. Fix: @SequenceGenerator(sequenceName="hibernate_sequence", allocationSize=1) or quarkus.hibernate-orm 'legacy' db_structure_naming_strategy.

10. [wrong-semantics | SURVIVES compile; runtime CNFE] pom.xml — com.enterprise:audit-logging-library:1.0.0 remains scope=system (systemPath lib/…jar); compiles, but Quarkus excludes system-scoped deps from the application model → ClassNotFoundException for com.enterprise.audit.logging.* when OrderService saves the first order. Fix: mvn install:install-file + normal compile dependency (note lib/ also has a 2.0.0 jar).

11. [incomplete | SILENTLY SURVIVES] src/main/webapp/** orphaned by WAR→JAR: entire AngularJS storefront, index.jsp, health.jsp, keycloak.json, web.xml are in a directory jar packaging never serves (Quarkus serves only META-INF/resources; JSP unsupported) — the migrated demo has REST endpoints but no UI, and no recorded decision about the trade-off.

12. [incomplete | SILENTLY SURVIVES] application.properties — prod inherits jdbc:h2:mem:coolstoredb (data evaporates on restart; original was server-managed CoolstoreDS) and no %prod amqp-host/port/credentials, so prod messaging defaults to anonymous localhost:5672. Fine for demo, must be a stated caveat.

13. [incomplete | latent, SURVIVES] pom.xml — jakarta.json (Transformers.java) and jakarta.xml.bind @XmlRootElement (InventoryEntity.java) compile only via lucky transitives (quarkus-smallrye-health→quarkus-jsonp; quarkus-hibernate-orm→jakarta.xml.bind-api). smallrye-health is itself scope creep (no backing insight) — stripping it as creep breaks the build. Add explicit quarkus-jsonp (+ jakarta.xml.bind-api or delete the unused @XmlRootElement).

14. [incomplete/cosmetic | SURVIVES] Dead code + inert verification: plan-mandated ShippingServiceRemote.java deletion skipped; src/main/java/weblogic/** stubs and persistence/Resources.java orphaned; maven.test.skip=true makes the plan's mvn test step a no-op (no src/test exists at all); finalName=ROOT is a WAR relic. Conversely verified-good and not to re-litigate: all 14 ee-to-quarkus-00020 @Transactional conversions, StartupListener→StartupEvent/ShutdownEvent, javax→jakarta sweep (only legal javax.sql.DataSource remains), persistence.xml/beans.xml deletion with faithful H2+hibernate-orm config, Producers.java @Produces Logger correctly retained.

## Validate-stage forecast
- 1. First mvn invocation fails BEFORE compilation at POM model validation: "'dependencies.dependency.version' for io.quarkus:quarkus-rest-jackson:jar is missing. @ line 37" (artifact not managed by the 3.8.4 BOM). One-line fix: artifactId → quarkus-resteasy-reactive-jackson.
- 2. Second mvn compile run: exactly two javac errors in src/main/java/com/redhat/coolstore/utils/DataBaseMigrationStartup.java — [35,29] 'constructor Flyway in class org.flywaydb.core.Flyway cannot be applied' (new Flyway()) and [36,19] 'cannot find symbol: method setDataSource(javax.sql.DataSource)'. Fix: delete the class (quarkus.flyway.migrate-at-start=true covers it).
- 3. Third run: mvn compile is GREEN. A compile-only validate stage stops here and reports success on an app that cannot start — everything below leaks into the demo PR unless validate goes further.
- 4. If validate runs mvn package: succeeds on JDK 17/21 (empirically verified — @SessionScoped does NOT fail augmentation on 3.8.4). ENVIRONMENT TRAP: on JDK 23+ package fails Hibernate bytecode enhancement ('Java NN is not supported by the current version of Byte Buddy') — pin the build JDK to 17/21 or pass -Dnet.bytebuddy.experimental=true.
- 5. If validate starts the packaged app (prod profile): startup hard-fails with jakarta.enterprise.inject.spi.DeploymentException SRMSG00073 'the following channel names cannot be used for both incoming and outgoing: [orders]'.
- 6. If validate runs mvn quarkus:dev instead: startup fails with 'Found 3 deployment problems' — channels 'orders' (x2) and 'inventory-notifications' configured with unknown connector (smallrye-in-memory); after deleting the %dev lines, testcontainers tries to start an AMQP Dev Service and fails without Docker ('Could not find a valid Docker environment') unless quarkus.amqp.devservices.enabled=false.
- 7. Never surfaced by any build/startup step (will silently reach the demo): first /cart request → ContextNotActiveException (@SessionScoped, no undertow); first checkout persist → sequence-not-found (ORDERS_SEQ vs Flyway's hibernate_sequence) and/or ClassNotFoundException com.enterprise.audit.logging.* (system-scoped jar excluded from fast-jar); inventory-notifications channel never fires; /services/* 404s; one global cart shared across users; no UI served from src/main/webapp.

## Instruction tuning for the workload
- REMEDIATE — BOM discipline: "Cross-check every versionless io.quarkus dependency against the pinned quarkus.platform.version BOM before writing it: on 3.8 LTS the REST stack is quarkus-resteasy-reactive-* (quarkus-rest-* names exist only from 3.9), and the AMQP extension is quarkus-smallrye-reactive-messaging-amqp. Never mix artifact names from different platform generations."
- REMEDIATE — extension-replaces-library rule: "When you add a Quarkus extension that replaces a manually-configured library (quarkus-flyway for flyway-core, quarkus-hibernate-orm for persistence.xml), DELETE the bootstrap/startup class the extension obsoletes instead of porting its API; the extension's config properties (e.g. quarkus.flyway.migrate-at-start=true) are the replacement. After removing any version-pinned dependency, grep for its API usage in code."
- REMEDIATE — messaging topology: "Before converting JMS, write a producer → broker-address → consumers table for the original app and assert the converted app preserves it: every @Incoming channel must have a producer; a channel name must never appear as both mp.messaging.incoming.* and mp.messaging.outgoing.* (use distinct names joined by .address); JMS Topic fan-out must be preserved via @Broadcast/in-process wiring or a multicast address, never by splitting subscribers onto addresses nobody publishes to."
- REMEDIATE — classpath honesty: "Never reference a connector, annotation, or class whose artifact is not in <dependencies> — after editing, verify each configured connector (e.g. smallrye-in-memory) and each new import maps to a declared dependency, and declare explicit dependencies for directly-imported APIs (quarkus-jsonp for jakarta.json, jakarta.xml.bind-api for JAXB) rather than relying on transitives."
- REMEDIATE — deletion postconditions: "Before deleting a JAX-RS Application class, capture its @ApplicationPath value and re-apply it as quarkus.resteasy-reactive.path. Treat every plan-mandated deletion as a verifiable postcondition (test ! -f), and when switching WAR→JAR record an explicit disposition for src/main/webapp (move static content to src/main/resources/META-INF/resources or state that the UI is dropped)."
- REMEDIATE — stateful conversion: "When converting @Stateful beans, key the per-user state by an identifier already present in the API (e.g. Map<cartId, ShoppingCart>) instead of merely widening the scope to @ApplicationScoped; do not leave @SessionScoped on REST endpoints unless quarkus-undertow is added — prefer @RequestScoped."
- REMEDIATE — misc hard rules: "Flag system-scoped dependencies as unsupported by Quarkus packaging (install-file + normal compile scope, not merely ugly); address Hibernate 6 implicit-sequence-naming insights by pinning @SequenceGenerator to the sequence your Flyway scripts actually create; remove maven.test.skip=true if you add surefire/failsafe."
- VALIDATE — the gate: "mvn compile green is NOT success. The gate is: (1) mvn package -DskipTests on JDK 17/21 (Quarkus 3.8 augmentation fails on JDK 23+ ByteBuddy), then (2) start the app (java -jar target/quarkus-app/quarkus-run.jar or quarkus:dev) and confirm clean startup — CDI scope errors, SmallRye wiring errors (SRMSG00073), and unknown-connector failures only surface at augmentation/startup, never at compile."
- VALIDATE — expected fix script for this run: "Fix in this order and re-run between steps: (1) pom.xml artifactId quarkus-rest-jackson → quarkus-resteasy-reactive-jackson; (2) delete src/main/java/com/redhat/coolstore/utils/DataBaseMigrationStartup.java (redundant with quarkus.flyway.migrate-at-start); (3) rename the consumer channel off 'orders' or remove connector config for in-process wiring; (4) delete the %dev smallrye-in-memory lines and set quarkus.amqp.devservices.enabled=false if no Docker; (5) change CartEndpoint to @RequestScoped. Do not stop at the first green compile."
- VALIDATE — silent-failure checklist: "After startup succeeds, explicitly verify what compile cannot: every @Incoming channel receives messages end-to-end (checkout → order persisted → inventory notification fires), REST paths match the demo script (/services prefix), first order insert succeeds (sequence naming + audit-logging classpath), and note prod caveats (in-mem H2, no AMQP broker config) in the PR description."
